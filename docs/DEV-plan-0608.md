# 早睡自救局架构优化方案：不改 UI 的代码框架收敛

更新时间：2026-06-08

## Summary

本轮只做代码框架和系统架构优化，不改交互、不改 UI 样式、不改页面视觉、不调整用户路径。

目标是把 16 周上线版从“功能完整”收敛到“长期可维护、可测试、可复用、可交给新 AI 流继续迭代”的工程状态。

## Optimization Principles

- UI 等价：页面布局、颜色、文案、按钮、导航入口保持当前表现。
- 行为等价：用户完成自救、复盘、睡意生成、监听、打卡、成长查看的路径不变。
- 架构收敛：减少双数据源、重复状态判断、巨型页面文件和隐性业务规则。
- 可交接：每个改动都要能说明“为什么做、解决什么问题、后续如何复用”。

## Architecture Changes

- 收敛数据事实源：以 SQLite + `DailyCycle` 作为每日闭环唯一事实源；旧 Zustand/AsyncStorage 日记录只做迁移兼容。
- 集中状态推进：把每日闭环状态推进统一放到 daily-cycle 核心模块，页面不再各自判断状态优先级。
- 页面瘦身但不改 UI：从大页面中抽出取数、view model、业务动作，保留原 JSX 和样式表现。
- 同步架构强化：让 `sync_queue` 承担离线 pending operation，全量推拉保留为兜底。
- 观测事件类型化：埋点事件名和属性做强类型，继续保持脱敏规则。
- 新增迭代说明记录：每一步都记录本质原因、目的和复用提示，方便后续 AI 直接理解本轮优化意图。

## Implementation Plan With Rationale

| Step | Action | 本质原因 | 目的 |
| --- | --- | --- | --- |
| 1 | 建立架构基线，跑 `npm.cmd run verify:release`，梳理旧 Zustand/AsyncStorage 与 SQLite 的依赖点 | 现在项目已经上线化，不能在没有基线的情况下移动核心代码 | 确保后续每次重构都能证明“没有破坏当前功能” |
| 2 | 新建或整理 `src/features/daily-cycle/`，集中状态 rank、状态推进、默认记录创建、睡眠结果计算 | 每日闭环是产品主轴，当前状态逻辑分散在页面和 storage 中 | 让新 AI 或新开发者先理解 DailyCycle，就能理解整个 App 主流程 |
| 3 | 将 `dailyExecutionStorage` 改成薄封装，核心业务规则迁入 daily-cycle service | storage 层不应该承载太多产品规则，否则数据读写和业务判断混在一起 | 后续新增状态、同步、测试时，不需要翻多个页面找规则 |
| 4 | 抽离首页逻辑，例如 `useHomeData`、`buildHomeViewModel`，但保持首页 UI 不变 | `app/index.tsx` 既负责取数、状态决策、导航，也负责渲染，后续容易误改 UI | 让首页的“当前最该做的一件事”成为可测试、可复用的纯逻辑 |
| 5 | 抽离自救流程逻辑，例如 `buildRescueViewModel`、自救 use-case，保持自救页表现不变 | 自救页是主流程核心，状态判断和用户动作耦合较重 | 保证自救三步流程稳定，后续 AI 接手时不会随手改坏路径 |
| 6 | 抽离成长页数据计算与展示组装，保留当前视觉 | `records.tsx` 文件过大，增长数据、图表、徽章、周总结入口混在一起 | 降低成长页维护成本，让数据计算和 UI 展示边界更清晰 |
| 7 | 抽离设置页保存、清空、删除账号、提醒调度 use-case | 设置页涉及配置、权限、提醒、账号删除，副作用较多 | 让危险动作有明确入口，避免后续误删数据或漏取消提醒 |
| 8 | 将旧 AsyncStorage 日记录降级为迁移兼容层，新写入只进 SQLite | 双写和双读会让状态来源不确定，长期会产生“页面显示和同步数据不一致” | 统一事实源，同时保护老用户历史数据 |
| 9 | 落地 `sync_queue`：本地写入生成 queue item，联网逐条同步，失败记录 attempts 和 lastError | 16 周计划里已有离线队列设计，但当前更偏全量推拉 | 提升弱网和断网恢复能力，也方便定位到底是哪类数据同步失败 |
| 10 | 强类型化 analytics event 和属性 schema | 埋点现在能用，但事件名和属性仍容易写错 | 让监控数据更可靠，后续分析闭环完成率、AI fallback、同步失败更可信 |
| 11 | 为本轮新增一份架构说明文档，例如 `docs/05-development/architecture-optimization-rationale.md` | 用户明确希望后续新 AI 流能马上知道本轮迭代目的 | 把“为什么这么改”固化到项目文档，不只存在聊天记录里 |
| 12 | 回归验证：typecheck/lint + 核心路径人工核对 | 架构重构最怕行为等价被破坏 | 确认 UI、交互、核心流程、数据迁移、同步恢复都保持稳定 |

## Documentation Requirement

本轮说明文档应记录：

- 本轮优化边界：不改 UI、不改交互、不新增功能。
- 本轮核心目标：事实源收敛、状态规则集中、页面瘦身、同步队列落地。
- 每个步骤的本质原因和目的。
- 新 AI 接手提示：优先读 `DailyCycle`、daily-cycle service、同步队列，再看页面。
- 禁止事项：不要为了重构改视觉，不要把业务规则重新写回页面，不要新增第二套状态源。

## Test Plan

- `npm.cmd run verify:release` 必须通过。
- 旧 AsyncStorage 数据能迁移到 SQLite，重启后记录仍存在。
- DailyCycle 状态重复触发时只前进不倒退。
- 首页、自救、复盘、睡意生成、睡眠监听、次日打卡、成长页、设置页表现保持一致。
- 断网完成记录后生成同步队列，恢复网络后可同步，失败可重试且不覆盖本地数据。

## Assumptions

- 本轮不新增功能。
- 本轮不改 UI 样式和交互路径。
- 不调用浏览器，除非用户单独批准。
- 只有在用户明确要求执行后，才进入代码实现阶段。
